### Ключевая идея

LLM рассматривается не как единый "мозг", а как **команда из 8 специалистов**, каждый со своей зоной ответственности, инструментами и артефактами.

**Преимущества подхода**:
- Чёткое разделение ответственности
- Явные точки контроля (quality gates)
- Предсказуемые результаты
- Возможность отката к конкретной роли при проблемах

## Роль 1: Analyst (Аналитик)

### Карточка роли

| Параметр | Значение |
|----------|----------|
| **Номер в пайплайне** | 1 (первый) |
| **Команда запуска** | `/idea` |
| **Управляющий документ** | `conventions.md`, `CLAUDE.md` |
| **Доступные инструменты** | Read, Glob, Grep, Write |
| **Режим работы** | Чтение + Запись |

### Что делает

Analyst — это "бизнес-аналитик" команды. Он:

1. **Собирает требования** от заказчика/пользователя
2. **Задаёт уточняющие вопросы** для устранения неопределённости
3. **Формулирует PRD** (Product Requirements Document)
4. **Определяет критерии успеха** (success metrics)

### Входящие данные

- Сырая идея от пользователя
- Контекст проекта
- Существующие `conventions.md`
- Бизнес-ограничения

### Выходящие данные

**Путь к артефакту**: `docs/prd/<ticket>.prd.md`

**Ключевые результаты**:
- PRD документ со всеми требованиями
- **Первичный Пайплайн Фичи** — высокоуровневые этапы реализации

## Роль 2: Researcher (Исследователь)

### Карточка роли

| Параметр | Значение |
|----------|----------|
| **Номер в пайплайне** | 2 (второй) |
| **Команда запуска** | `/researcher` |
| **Управляющий документ** | `conventions.md` |
| **Доступные инструменты** | Read, Glob, Grep |
| **Режим работы** | **Только чтение (READ-ONLY)** |

### Что делает

Researcher — это "разведчик" команды. Он:

1. **Исследует существующую кодовую базу**
2. **Маппит зависимости** между модулями
3. **Выявляет используемые паттерны**
4. **Идентифицирует ограничения** и технический долг
5. **Находит точки интеграции** для новой фичи

### Входящие данные

- PRD от Analyst
- Существующая структура проекта
- `conventions.md`
- Текущий технический стек

### Выходящие данные

**Путь к артефакту**: `docs/research/<ticket>.md`

**Ключевые результаты**:
- Research Report с анализом кодовой базы
- **Уточнённый Пайплайн Фичи** — детализированные этапы с учётом constraints

## Роль 8: Validator (Валидатор)

### Карточка роли

| Параметр | Значение |
|----------|----------|
| **Номер в пайплайне** | 8 (восьмой, мета-роль) |
| **Команда запуска** | `/validate` |
| **Управляющий документ** | `workflow.md`, gate definitions |
| **Доступные инструменты** | Read, Glob, Grep |
| **Режим работы** | **Только чтение (READ-ONLY)** |

### Что делает

Validator — это "контролёр качества процесса". Он:

1. **Проверяет все quality gates** — прошли ли они
2. **Выявляет пропущенные шаги** в процессе
3. **Идентифицирует blockers** для релиза
4. **Генерирует summary статус** всего пайплайна

### Входящие данные

- PRD (Analyst output)
- Research Report (Researcher)
- Implementation Plan (Architect)
- Tasklist status
- Code (Implementer output)
- Review Report (Reviewer)
- QA Report
- Documentation (Tech Writer)

### Выходящие данные

**Путь к артефакту**: `reports/validation/<ticket>.md`
