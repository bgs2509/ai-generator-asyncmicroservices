    Ключевая идея¶

    LLM рассматривается не как единый "мозг", а как команда из 8 специалистов, каждый со своей зоной ответственности, инструментами и артефактами.

    Преимущества подхода: - Чёткое разделение ответственности - Явные точки контроля (quality gates) - Предсказуемые результаты - Возможность отката к конкретной роли при проблемах

    Карточка роли¶

    Параметр Значение
    Номер в пайплайне 1 (первый)
    Команда запуска /idea

    Порядок чтения документов для Analyst¶

    Фаза 1: Контекст фреймворка (обязательно)

    1. AGENTS.md — точка входа, обзор фреймворка
    2. docs/reference/agent-context-summary.md — критические правила
    3. docs/guides/ai-code-generation-master-workflow.md — 7-стадийный процесс
    4. docs/reference/maturity-levels.md — 4 уровня зрелости

    Фаза 2: Валидация промпта (обязательно)

    1. docs/guides/prompt-validation-guide.md — 10 обязательных полей
    2. docs/reference/prompt-templates.md — шаблоны уточняющих вопросов

    Фаза 3: Требования (после успешной валидации)

    1. docs/guides/requirements-intake-template.md — шаблон сбора требований
    2. docs/guides/requirements-traceability-guide.md — жизненный цикл Req ID

    Что делает¶

    Analyst — это "бизнес-аналитик" команды. Он:

    1. Загружает контекст фреймворка (Стадия 0: Инициализация)
    2. Читает AGENTS.md, agent-context-summary.md, ai-code-generation-master-workflow.md

    3. Изучает maturity-levels.md для понимания 4 уровней зрелости

    4. Валидирует полноту промпта (Стадия 1: Валидация промпта)

    5. Проверяет 10 обязательных полей по prompt-validation-guide.md
    6. Идентифицирует блокеры (Бизнес-контекст, Уровень зрелости, Функциональные требования)

    7. Использует шаблоны из prompt-templates.md для уточнений

    8. Задаёт уточняющие вопросы для устранения неопределённости

    9. Применяет политику повторных попыток (макс. 3 попытки)
    10. Чётко указывает какие поля отсутствуют и почему они критичны

    11. При отсутствии ответа — корректное завершение

    12. Формулирует PRD (Product Requirements Document)

    13. Заполняет структуру requirements-intake-template.md
    14. Присваивает уникальные Req ID (FR-, UI-, NF-*) каждому требованию

    15. Фиксирует целевую конфигурацию (уровень зрелости, модули, время генерации)

    16. Определяет критерии успеха (метрики)

    17. KPI и бизнес-метрики

    18. Критерии приёмки для верификации

    19. Определяет Первичный Пайплайн Фичи

    20. Высокоуровневые этапы реализации
    21. Критический путь
    22. Предварительные риски пайплайна

    Чеклист валидации промпта¶

    Поле Почему критично Блокер?
    Бизнес-контекст Определяет проблему, пользователей, метрики успеха ✅ Да
    Целевой уровень зрелости Определяет инфраструктуру, время генерации (1-4) ✅ Да
    Функциональные требования Определяет возможности сервисов ✅ Да
    Опциональные модули Workers, Bot, MongoDB, RabbitMQ, Redis Нет (по умолчанию: none)
    Нефункциональные ограничения Архитектура, производительность, безопасность ✅ Да
    Зависимости и интеграции Внешние системы, очереди, источники данных ✅ Да
    Границы скоупа Предотвращает незапланированные фичи ✅ Да
    Ожидаемые артефакты Выравнивает результаты с ожиданиями ✅ Да
    Критерии приёмки Измеримые проверки успеха Нет
    Открытые вопросы и риски Ранняя идентификация неизвестного Нет

    ПРАВИЛО: Если любое поле-блокер отсутствует → НЕЛЬЗЯ переходить к Стадии 2. Используй шаблоны из prompt-templates.md для запроса недостающей информации.

    Роль 2: Researcher (Исследователь)¶

    Карточка роли¶

    Параметр Значение
    Номер в пайплайне 2 (второй)
    Команда запуска /researcher
    Управляющий документ conventions.md
    Доступные инструменты Read, Glob, Grep
    Режим работы Только чтение (READ-ONLY)

    Что делает¶

    Researcher — это "разведчик" команды. Он:

    1. Исследует существующую кодовую базу
    2. Маппит зависимости между модулями
    3. Выявляет используемые паттерны
    4. Идентифицирует ограничения и технический долг
    5. Находит точки интеграции для новой фичи
    6. Задаёт уточняющие вопросы для устранения неопределённости

    • Существующая структура проекта

    Роль 7: Tech Writer (Технический писатель)¶

    Карточка роли¶

    Параметр Значение
    Номер в пайплайне 7 (седьмой)
    Команда запуска /docs-update
    Управляющий документ Documentation standards
    Доступные инструменты Read, Write, Glob, Grep
    Режим работы Чтение + Запись

    Что делает¶

    Tech Writer — это "документатор" команды. Он:

    1. Обновляет CHANGELOG с описанием изменений
    2. Обновляет архитектурную документацию
    3. Создаёт/обновляет API документацию
    4. Пишет runbooks и guides
    5. Обеспечивает onboarding-ready документацию

    Входящие данные¶

    • PRD от Analyst
    • Implementation Plan от Architect
    • Tasklist (выполненные задачи)
    • QA Report
    • Code changes

    Выходящие данные¶

    • Updated CHANGELOG.md
    • Updated architecture docs
    • Updated/new API docs
    • Runbooks/deployment guides
    • Updated README.md (если нужно)

    Роль 8: Validator (Валидатор)¶

    Карточка роли¶

    Параметр Значение
    Номер в пайплайне 8 (восьмой, мета-роль)
    Команда запуска /validate
    Управляющий документ workflow.md, gate definitions
    Доступные инструменты Read, Glob, Grep
    Режим работы Только чтение (READ-ONLY)

    Что делает¶

    Validator — это "контролёр качества процесса". Он:

    1. Проверяет все quality gates — прошли ли они
    2. Выявляет пропущенные шаги в процессе
    3. Идентифицирует blockers для релиза
    4. Генерирует summary статус всего пайплайна

    Входящие данные¶

    • PRD (Analyst output)
    • Research Report (Researcher)
    • Implementation Plan (Architect)
    • Tasklist status
    • Code (Implementer output)
    • Review Report (Reviewer)
    • QA Report
    • Documentation (Tech Writer)
